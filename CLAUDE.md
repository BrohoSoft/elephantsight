# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Cos'è

ElephantSight (prima WatchStore, nome che resta nell'indirizzo di produzione `watchstore.brohosoft.com`; nel codice ancora `Flarelytics`: namespace, progetti, database, volumi) è uno strumento **self-hosted** (un'immagine Docker + PostgreSQL) per gestire le proprie app su App Store e Google Play da un pannello solo. Un'istanza ha più organizzazioni (tenant); un'organizzazione ha più progetti; ogni progetto collega al massimo un'app App Store e un'app Google Play, attraverso le chiavi degli store caricate dall'utente (il .p8 di Apple, il JSON di un service account Google). Non c'è registrazione libera: il primo utente lo crea l'installer (`/setup`, finché non esistono utenti), gli altri entrano per invito. Niente pagamenti né fatturazione.

Stato: account con 2FA, organizzazioni con membri e inviti, chiavi cifrate, dashboard dei download App Store + Google Play, icone, e la gestione delle app: versioni e build, recensioni unificate con risposta, pagina dello store (testi e screenshot), cassaforte dei file di firma, caricamento delle build (.aab su Google Play, .ipa su App Store Connect), e un calendario per programmare post su Bluesky, Mastodon, Instagram (anche Reel), Pagine Facebook, TikTok e Threads, anche ricorrenti. La gestione è testata contro store simulati: con chiavi vere serve una chiave Apple Admin/App Manager e un service account Google con permessi di rilascio, scheda e recensioni. Essendo self-hosted, chi installa usa le API per le proprie app: è l'uso consentito dai termini di Apple e Google (compresa la Publishing API di Google, che prima andava evitata).

Codice, commenti e messaggi d'errore sono in italiano; i commenti spiegano il *perché*. Mantieni lo stesso stile.

## Comandi

```bash
docker compose -f compose.dev.yaml up -d                          # PostgreSQL di sviluppo su :5433
cd Flarelytics.Api && dotnet run                                   # API + sincronizzazione su http://localhost:5080, Scalar su /scalar
cd Flarelytics.Web && npm install && npm run dev                   # pannello su http://localhost:5173 (proxy /api → 5080)
cd Flarelytics.Web && npm run build                                # typecheck + build di produzione
docker compose up -d --build                                       # l'installazione vera (immagine unica + PostgreSQL), con .env: DB_PASSWORD, PUBLIC_URL
dotnet build
dotnet test                                                        # serve Docker (Testcontainers)
dotnet test --filter "FullyQualifiedName~CredentialTests"          # una classe
dotnet test --filter "FullyQualifiedName~SecretVaultTests.Un_byte_alterato_si_riconosce"   # un test
dotnet ef migrations add <Nome> --project Flarelytics.Core --startup-project Flarelytics.Core --output-dir Database/Migrations
```

In sviluppo le chiavi delle app social e `Social:PublicUrl` si mettono negli user-secrets (`cd Flarelytics.Api && dotnet user-secrets set "Social:Instagram:AppId" …`), non in `appsettings.Development.json`. In sviluppo le email non partono: i link si leggono nel log dell'API. L'SMTP è facoltativo anche in produzione (`/api/v1/instance` dice al pannello se c'è): senza, gli inviti restituiscono il link da copiare. La chiave master (e quella dei JWT se `Jwt:Key` manca) si crea da sola in `Secrets:KeysDirectory` con `Secrets:CreateKeyIfMissing` (attivo in Development e nell'immagine Docker). `dotnet run --environment` non imposta l'ambiente: usa il launch profile oppure `ASPNETCORE_ENVIRONMENT=Development`.

## Architettura

- **Flarelytics.Core**: modello EF, isolamento dei tenant, cifratura, client degli store, sincronizzazione (`Sync/`, con `SyncWorker` che chiama `SyncCoordinator.RunOnceAsync` ogni `Sync:PollInterval`).
- **Flarelytics.Api**: minimal API sotto `/api/v1`, un file per feature in `Features/` (handler statici, richieste, validatori FluentValidation nello stesso file). Ospita anche la sincronizzazione (`Worker:Enabled`, spenta nei test) e, nell'immagine Docker, serve il pannello da `wwwroot` (`Common/Frontend.cs`, che mette anche gli header di sicurezza/CSP). Deve girare in **una sola istanza**.
- **Flarelytics.Tests**: integrazione con Testcontainers (un database per test) e unit test. `MigrationTests` applica le migration una per volta sopra dati già presenti: una colonna NOT NULL nuova vuole un valore predefinito, altrimenti in produzione l'API non parte.
- **Flarelytics.Web**: React 19 + Vite + Tailwind 4 + TanStack Query + React Router, stile Supabase con tema chiaro, scuro o di sistema: i colori sono variabili CSS in `src/styles.css` (`@theme inline` → `var(--…)`, una palette per `[data-theme]`); `public/theme.js` applica il tema prima del primo disegno (file e non script inline, per la CSP) e `src/theme.ts` lo gestisce dopo. Per un colore nuovo serve un valore in entrambe le palette. Componenti base in `src/components/ui.tsx`, tipi delle risposte scritti a mano in `src/api/types.ts` (da allineare ai record C#). In produzione lo serve l'API (il `Dockerfile` alla radice lo compila e lo copia in `wwwroot`).

### Isolamento dei tenant: due livelli, entrambi obbligatori
1. Le entità `ITenantOwned` ricevono un filtro globale EF su `TenantContext.TenantId` (`FlarelyticsDbContext`). Con il tenant non impostato le tabelle appaiono vuote.
2. Row-Level Security di PostgreSQL. `TenantConnectionInterceptor` scrive `app.tenant_id` a ogni apertura di connessione; le politiche sono create in migration con `RowLevelSecurity.Enable(...)`. **Una nuova tabella `ITenantOwned` ha bisogno della sua chiamata `RowLevelSecurity.Enable` nella migration**: non è automatico.

`TenantContext.Set` si chiama solo in `OrgAccessFilter` (tutte le rotte `/orgs/{orgId}/...`, che controllano la membership e il ruolo), in `ApiKeyFilter` (le rotte `/public/...`, dalla chiave API) e nel worker, tenant per tenant. Se la richiesta usa una transazione esplicita, il tenant va impostato prima di aprirla. L'app deve collegarsi con un ruolo **non superutente e senza BYPASSRLS**, proprietario delle tabelle: per questo le politiche sono `FORCE`. I test fanno lo stesso (`PostgresFixture`), altrimenti i test sulla RLS passerebbero senza verificare niente.

### Accesso per membro: progetti e sezioni
Oltre al ruolo (`OrgRole`: Viewer, Admin, Owner = cosa può fare), ogni `Membership` (e ogni `Invitation`, che la diventa) ha un `MemberAccess` = dove: `AllProjects` o una lista `ProjectIds`, e `Sections` (`AppSections.Store` e/o `Social`). L'owner vede sempre tutto. `OrgAccessFilter` controlla, oltre al ruolo, la sezione della rotta (`RequireSection`), l'accesso completo (`RequireFullAccess`: membri, inviti, chiavi API, chiavi degli store, account social da collegare o assegnare, creazione/modifica dei progetti, nome dell'organizzazione) e il `{projectId}` della rotta (404 se non visibile). Le liste che mescolano progetti le filtra l'handler con `CurrentOrg.VisibleProjects` (null = tutti); un dato senza progetto (un post dell'organizzazione) lo vede solo chi vede tutti i progetti. **Una rotta nuova sotto un progetto o una sezione va marcata**, e una lista nuova va filtrata: non è automatico come il tenant. Nel modello niente `HasDefaultValue` per `AllProjects`/`Sections` (EF scambierebbe `false`/`None` per "non impostato"): i default per le righe vecchie (tutto visibile) stanno solo nella migration `ProjectAccess`. Il pannello costruisce menu e rotte da `OrgSummary.Access` (`components/org.ts`: `hasStore`, `hasSocial`, `isFull`, `canManageOrg`).

`Tenant`, `User`, `Membership`, `RefreshToken`, `EmailToken`, `ApiKey` non sono del tenant: si leggono prima di aver scelto un tenant (nelle rotte del pannello si filtrano per tenant a mano).

### Credenziali degli store
- Metadati (Key ID, Issuer ID, email del service account, bucket) in `StoreCredential`; il segreto vero solo cifrato su disco tramite `SecretVault`. Nessuna rotta restituisce il segreto.
- Cifratura a busta: una DEK casuale per file (AES-256-GCM), cifrata con la chiave master (KEK) versionata letta da `Secrets:KeysDirectory`. Tenant e credenziale entrano come dati associati, quindi un file spostato non si decifra. Rotazione: nuova chiave + `ActiveKeyVersion` + `SecretVault.RewrapAsync`.
- Il segreto si usa solo tramite `CredentialSecrets.UseAsync`, che lo azzera dopo l'uso.
- Al caricamento: parse (`AppleKey`/`GoogleServiceAccount`) → verifica con lo store (`IStoreGateway`) → cifratura → salvataggio. `Rejected` non si salva; `Limited` sì, con l'avviso (i permessi di Google Play arrivano ore dopo l'invito).
- Gateway senza SDK: JWT ES256 firmato da noi per Apple; JWT RS256 scambiato con un token OAuth per Google (`GoogleAuth`).
- Google: verifica della chiave ed elenco delle app passano dal bucket GCS `pubsite_prod_…` (le app dai nomi dei file). Il codice è nato quando ElephantSight doveva essere un SaaS e i termini della Play Developer Reporting/Publishing API vietavano di usarle con l'account di un terzo; da self-hosted quelle API si possono usare (servono per build, listing, recensioni).
- `ProjectApp.ExternalAppId` è l'Apple ID numerico (non il bundle id) oppure il package name Android.

### Sincronizzazione e metriche (fase 2)
- Flusso: `SyncCoordinator` → cambi BCE (`RatesRefresher`) → per ogni tenant apre uno scope, imposta `TenantContext` (la RLS vale anche nel worker) e chiama `AppleSalesSync` per le credenziali App Store da sincronizzare (ogni `Sync:Interval`, o subito con "Sincronizza ora" = `SyncRequestedAtUtc`).
- `AppleSalesSync` scarica SALES/SUMMARY/DAILY versione `1_0` per ogni giorno mancante degli ultimi `BackfillDays` (dal più recente), e ritenta i giorni vuoti recenti: Apple risponde 404 sia per "nessuna vendita" sia per "non ancora pronto". I giorni seguono il fuso del Pacifico (`AppleCalendar`). 401 rende la chiave `Invalid`, 403 `Limited`.
- Google Play: `GooglePlaySync` legge `stats/installs/installs_<package>_<aaaamm>_country.csv` (UTF-16, colonne per nome con alternative; Download = "Daily User Installs"), riscarica un file mensile solo se cambia l'MD5, e riscrive solo le colonne delle installazioni (download, aggiornamenti, disinstallazioni).
- **Niente ricavi, per scelta di prodotto**: si mostrano solo download, riscaricamenti, aggiornamenti e disinstallazioni. I report finanziari di Google (vendite, guadagni) non si scaricano. Le colonne dei ricavi in `DailyAppMetric` si riempiono ancora per Apple (vengono dallo stesso report dei download), ma l'API non le espone come coperte (`StoreCoverage`) e la UI non le mostra. Per i download Apple basta una chiave con ruolo **Sales**.
- Icone (`AppIcon`, tabella globale, non del tenant): il worker le scarica da iTunes Lookup (Apple, nei paesi con più download dell'app) e dall'`og:image` della pagina pubblica di Google Play. Servite anonime da `GET /api/v1/icons/{id}` con un Guid casuale, per non rivelare quali app sono seguite.
- I report grezzi (gzip, così come arrivano) stanno su disco tramite `ReportStorage` e sono la fonte di verità: `ReportProcessor` ne ricava `DailyAppMetric` senza rete. Cambiando il modo di contare si alza `AppleSalesAggregator.Version` e i file vengono rielaborati al giro successivo.
- `DailyAppMetric` (schema `metrics`, chiave tenant+store+app+giorno+paese, importi in micro-euro) è legata all'app, non al progetto: i progetti la leggono tramite `ProjectApp.ExternalAppId`. Gli acquisti in-app si attribuiscono all'app tramite lo SKU (`AppleAppSku`).
- Il parser legge le colonne per nome; per i rimborsi gli importi sono unità × |prezzo| (Apple scrive il prezzo negativo ma il ricavo positivo).
- Valute: conversione in euro con il cambio BCE del giorno (o fino a 7 giorni prima); un report senza cambi disponibili aspetta. Valute non quotate dalla BCE → `HasUnconvertedAmounts`.
- La firma dei JWT usa `AppStoreConnectGateway.UncachedSigning`: con la cache di IdentityModel il secondo token con la stessa chiave usava un oggetto già eliminato.
- La dashboard (`GET /orgs/{orgId}/metrics?days=&projectId=`) fa finire il periodo all'ultimo giorno con dati, non a oggi. Nel frontend `components/Dashboard.tsx` e `TrendChart.tsx` (barre impilate per store, un solo valore alla volta: mai due assi). I colori `--ios`/`--android` sono validati per contrasto e daltonismo in entrambi i temi: se cambiano, vanno rivalidati.

### Gestione delle app (`Core/Management`, `Api/Features/Manage`)
- Client: `AppleApi`/`AppleSession` (JSON:API letto come `JsonNode`, token firmato una volta per operazione, `UploadAsync` esegue le `uploadOperations` di Apple) e `GooglePublisher`/`GoogleSession` (Android Publisher API v3; quasi tutto dentro un **edit**: `WithEditAsync` lo conferma con `commit` o lo cancella sempre, anche in lettura e in caso di errore). Errori dello store → `StoreAccessException` con il messaggio dello store; ogni pagina mostra l'errore di uno store senza bloccare l'altro.
- Campi e endpoint verificati sulla specifica OpenAPI di App Store Connect (4.5) e sul documento discovery di androidpublisher v3: se cambiano, ricontrollare lì.
- Versioni/build (`ReleasesService`): lette live a ogni richiesta, stati ridotti a `ReleaseStage`.
- Recensioni (`ReviewsService`, `Review`, `ReviewSyncState`): copiate nel db dal worker (dopo la sync di ogni chiave) perché Google via API dà solo l'ultima settimana; risposta Apple = cancella e ricrea `customerReviewResponses`; Google `:reply` (max 350 caratteri).
- Pagina dello store (`ListingService`): Apple modifica nome/sottotitolo solo con appInfo in preparazione e descrizione/keywords/novità solo su versione in preparazione (il testo promozionale sempre); il servizio rifiuta con un messaggio chiaro invece di ignorare. Screenshot Apple: prenotazione → `uploadOperations` → PATCH con MD5. Google: listing e immagini dentro un edit confermato.
- File di firma (`ProjectSecretFile`): cifrati con `SecretVault` (id del file al posto di quello della credenziale), scaricabili solo da admin riconfermando password e TOTP.
- Build (`BuildUpload`, `BuildUploader`, `BuildUploadWorker`): la richiesta salva il file in streaming (`MultipartReader`, fino a 4 GB) in `{Reports}/_uploads` e lo mette in coda; il worker, ogni 10 s, lo manda allo store. Google: bundle + track (stato, `userFraction`, note) + commit nello stesso edit. Apple: API Build Uploads (4.1+) con versione/build letti dall'`Info.plist` dell'.ipa (`IpaReader`, anche binario), poi segue l'elaborazione ogni minuto. Il file si cancella appena consegnato.
- Cancellare un progetto cancella anche i suoi file cifrati e le build in coda.
- Test: `FakeStoreServer` sostituisce l'HTTP dei client veri (`HttpClientFactoryOptions` per nome del tipo) e registra le richieste, così i test verificano anche cosa si manda agli store.

### Auth
Access token JWT (15 min) nel corpo della risposta, tenuto solo in memoria dal frontend (`src/api/client.ts`); refresh token (30 giorni, ruotato a ogni uso, rilevamento del riuso) in un cookie HttpOnly `SameSite=Strict` con path `/api/v1/auth` (`Secure` salvo `Auth:SecureCookies=false`, necessario in HTTP fuori da localhost). Per questo frontend e API stanno sulla stessa origine (l'API serve il pannello in produzione, proxy di Vite in sviluppo), e il frontend deve avere un solo refresh in volo per volta. Un cambio password ruota `SecurityStamp`, controllato a ogni richiesta in `OnTokenValidated`.

2FA TOTP (RFC 6238, implementazione propria in `Auth/Totp.cs`): il seme è cifrato in colonna con `FieldProtector` (stesse chiavi master del vault). Con la 2FA attiva il login risponde **202** con una `LoginChallenge` (a database, 5 tentativi) da completare su `/auth/login/2fa`; ogni intervallo TOTP vale una volta sola (`TotpLastUsedStep`). Codici di recupero salvati come hash SHA-256.

Installer (`Features/Setup`): `GET /instance` (`setupRequired`, `emailEnabled`) e `POST /setup`, che crea l'amministratore e la prima organizzazione sotto un `pg_advisory_xact_lock`, così due installer simultanei non creano due amministratori. Il pannello reindirizza tutto a `/setup` finché serve.

Inviti: `Invitation` e `Membership` **non** sono `ITenantOwned` (chi accetta non è ancora nel tenant), quindi in `MemberEndpoints` si filtra per tenant a mano. L'invito è nominativo (l'email deve coincidere), vale come conferma dell'email, ed è l'unico modo di registrarsi (`POST /auth/register` vuole sempre il token). La creazione restituisce il link una volta sola, per mandarlo a mano senza SMTP.

### Impostazioni dell'istanza e amministratori
SMTP, app social (Meta, Instagram, TikTok, Threads) e Bunny Storage (gruppo `bunny`: zone, regione, password della zone come segreto; `POST /instance/settings/bunny/test` scrive, rilegge e cancella un file di prova) si mettono anche dal pannello (`/instance`, `Features/Instance`): righe di `InstanceSetting` (tabella globale), **tutte cifrate** con `FieldProtector` (contesto `instance-setting|{chiave}`), elencate in `InstanceSettingCatalog` con il percorso di configurazione e se sono segrete (i segreti non tornano mai: la risposta dice solo se ci sono e da dove vengono, pannello o .env). `InstanceSettingsConfigurationSource` è aggiunta per ultima in `Program.cs`, quindi vince sul .env; `InstanceSettingsStore` la riempie all'avvio (dopo le migration) e a ogni salvataggio, e il ricaricamento arriva a chi legge con **`IOptionsMonitor`**: le opzioni social, l'SMTP e `MediaStorageOptions` vanno lette così (`CurrentValue`), non con `IOptions`, altrimenti un cambio dal pannello non si vede fino al riavvio. Un campo vuoto toglie il valore del pannello e torna a valere il .env. L'email si decide a ogni invio (`ConfiguredEmailSender`). Le rotte le apre solo `User.IsInstanceAdmin` (`InstanceAdminFilter`): ce l'ha chi fa l'installazione (e, con la migration, il primo utente di un'installazione esistente), e lo dà ad altri; è separato dai ruoli delle organizzazioni.

### Backup (`Core/Backups`, `Api/Features/Backups`)
- `BACKUPS_ENABLED` (`Backups:Enabled`, solo da ambiente) decide se la funzione esiste: falso = rotte non registrate (404), niente worker, gruppo `backup` nascosto dalle impostazioni (`InstanceSettingCatalog.IsAvailable`, la stessa regola del blocco di Bunny), `/instance` dice `backupsEnabled: false` e il pannello non mostra niente. Serve per un'istanza ospitata, dove i backup li fa chi la ospita. Tutto il resto (attivi, ora, fuso, ogni quanti giorni, quanti tenerne, password) sta nel gruppo `backup` delle impostazioni dell'istanza (`Backups:*`, `IOptionsMonitor`), validato in `InstanceEndpoints.ValidateBackup`.
- `BackupService`: un file `elephantsight-…esbk` in `Backups:Directory` (`/data/backups`, volume a parte) con manifest, `keys/`, `secrets/`, `reports/` (senza `_social`, `_social-tmp`, `_uploads`) e `database.dump` (`pg_dump -Fc`), scritti in streaming in `BackupArchiveWriter` (formato proprio a pezzi con lunghezza: tar vuole la lunghezza prima, pg_dump non la sa) dentro `BackupCipher` (PBKDF2-SHA256 dalla password, AES-256-GCM a blocchi da 1 MiB, indice e ultimo blocco nei dati associati). Niente in chiaro su disco. **Non** la chiave master: il backup la contiene.
- Il dump usa `ConnectionStrings:Backup` = ruolo `flarelytics_backup` (BYPASSRLS + `pg_read_all_data`, `deploy/postgres/20-backup-role.sh`, idempotente): il ruolo dell'app con la RLS FORCE non può fare il dump (`query would be affected by row-level security policy`) e non deve poterlo fare. `pg_dump`/`pg_restore` 17 vengono da PGDG nel `Dockerfile` (Ubuntu ha la 16, che il server 17 rifiuta).
- `BackupWorker` (ogni minuto, solo con `Worker:Enabled`): appuntamenti `BackupSchedule` = ora locale ogni N giorni contati da una data fissa; parte se dall'ultimo appuntamento non è partito nessun backup programmato (uno fallito non si ripete fino al prossimo). `BackupRunner` ne fa uno alla volta (quello manuale in background). `BackupRun` (tabella globale) è lo storico; all'avvio quelli aperti diventano "interrotti". Dopo un backup riuscito si tengono gli ultimi `Keep` file.
- Ripristino solo da riga di comando, a istanza ferma: `Program.cs` riconosce `restore [--check] [--yes] <file>` prima delle migration (`BackupCommand` → `BackupRestorer`): legge tutto il file per verificarlo, poi scrive chiavi/credenziali/report e fa `pg_restore --clean --if-exists --no-owner --single-transaction` con il ruolo dell'app (le politiche RLS sono nella sezione post-data del dump, quindi i dati entrano prima). Password da prompt o `BACKUP_PASSWORD`.
- Download dal pannello: `POST /instance/backups/files/{nome}/link` dà un indirizzo anonimo con un token DataProtection di 5 minuti (il file può essere grande: niente blob in memoria). I nomi accettati sono solo quelli del pattern (niente `../`).
- Test: `ContainerPgTools` esegue pg_dump/pg_restore con `docker exec` nel contenitore dei test (sul computer possono mancare); `PostgresFixture` crea anche il ruolo dei backup.

### Panoramiche
`GET /orgs/{orgId}/overview[?projectId=]` (`Features/Overview`) dà in una chiamata i numeri dei social (programmati, in coda, ricorrenti attivi, non usciti in 7 giorni), i prossimi 5 post comprese le uscite dei ricorrenti, i progetti visibili e, a chi gestisce l'organizzazione, gli ultimi 10 log; ogni parte segue l'accesso del membro. La panoramica dell'organizzazione (`pages/Overview.tsx`) aggiunge gli ultimi progetti aperti (localStorage, `components/recentProjects.ts`) e la versione in uso sugli store (dalla rotta delle versioni); i download stanno in `pages/Analytics.tsx` (Download) e, per progetto, nella scheda Analitiche. La panoramica del progetto mostra download dei 30 giorni, social del progetto e versioni.

### Log nel pannello
`StoredLogProvider` (registrato in `Program.cs` con `AddStoredLogs`) mette in coda i messaggi di ElephantSight dall'Information in su e di tutto il resto solo Warning+; `StoredLogWriter` li scrive a blocchi nella tabella globale `LogEntry` (non del tenant: si filtra a mano) e cancella quelli oltre 30 giorni. L'organizzazione di un messaggio è `TenantContext.Ambient` (AsyncLocal impostato da `TenantContext.Set`), l'area (Social, Store, Sistema) viene dalla categoria. La pagina Log (`/orgs/{orgId}/logs`) è per admin con accesso completo; i messaggi di sistema (senza organizzazione) li vede solo l'owner. Un messaggio utile in un log va scritto pensando che lo legga chi usa il pannello: cosa, dove (rete, account, id del post) e perché.

### Errori
Lancia `ApiProblem` (stato + `code` stabile + dettaglio). `ProblemExceptionHandler` lo trasforma in Problem Details e mappa anche le chiavi non valide (400), gli errori degli store (502) e le violazioni di vincoli unique (409). Il frontend ragiona sul `code`, non sul testo.

### Social (`Core/Social`, `Api/Features/Social`, `Web/src/social`, `Web/src/pages/social`)
- Un post **programmato** (e un post ricorrente) sta in un progetto se l'organizzazione ne ha almeno uno (`SocialPostEndpoints.HasProjectsAsync`, `project_required`); bozze e coda possono restare senza. Dalla coda (`/inbox?projectId=`, anche per progetto nel pannello) si programma con `AssignInboxRequest.ProjectId` per i post che non ne hanno; dall'API pubblica il progetto si può già mandare con `projectId`.
- Progetti: un `SocialAccount` è dell'organizzazione e si collega a uno o più progetti (`ProjectIds`, uuid[]; lo assegna chi ha accesso completo). Un post (e un post ricorrente) di un progetto usa solo gli account di quel progetto, anche in bozza (`SocialPostEndpoints.EnsureInProject`); chi vede solo alcuni progetti deve sceglierne uno (`project_required`). Il calendario dell'organizzazione mostra i post dei progetti visibili, quello del progetto (`/projects/{id}/social`, `projectId=`) solo i suoi. I post importati prendono il progetto dell'account se ne ha uno solo. Cancellare un progetto lo toglie da account, membri e inviti.
- Modello: `SocialAccount` (segreto cifrato in colonna con `FieldProtector`, contesto `SecretContext`), `SocialPost` (data sempre presente, anche per le bozze), `SocialPostTarget` (un esito per account, con copia di rete e nome: l'account scollegato lascia lo storico, `AccountId` → null), `SocialMedia` (caricato prima del post e attaccato al salvataggio; gli orfani li cancella il worker dopo un giorno; i file stanno sul disco o su Bunny, vedi sotto).
- File dei post (`Core/Social/Media`): **solo `SocialMediaStore`** scrive, legge, copia e cancella (publisher, pezzi di TikTok, copie dei ricorrenti e di "Duplica", rotta pubblica). Due backend: `LocalMediaBackend` (`{Reports}/_social/{tenant}/{id}.jpg|.mp4|.mov`, in chiaro, miniatura `{id}.thumb.jpg`) e `BunnyMediaBackend` (`BunnyStorageClient`, HttpClient senza SDK, header `AccessKey`, host per regione in `BunnyStorageOptions.Regions`; `elephantsight/social/{tenant}/{id}[.thumb].bin`: `BunnyStorageClient.RootFolder` mette tutto, anche la prova, sotto `elephantsight/`, mai nella radice della zone). I file nuovi vanno nello storage attivo (`Media:Storage` = Auto/Local/Remote, da `MEDIA_STORAGE`; Auto = Bunny se configurato), quelli vecchi si leggono e si cancellano dove dice `SocialMedia.Location` (default Local nella migration: niente da spostare). Con `Media:Locked` (`MEDIA_STORAGE_LOCKED`, solo ambiente) Bunny vale solo dal .env: `InstanceSettingCatalog.IsAvailable` toglie il gruppo `bunny` (niente lettura, salvataggio, prova; `InstanceSettingsStore.LoadAsync` ignora i valori già salvati) e `/instance` dice `mediaStorageLocked`, così il pannello non mostra la sezione e i messaggi rimandano a chi gestisce l'installazione. In Remote senza Bunny `WritableLocation` lancia `MediaStorageUnavailableException` → 503 `media_storage_unavailable`, `/instance` dice `mediaStorage: "unavailable"` e il pannello spegne i caricamenti; il testo funziona. Sul disco restano solo i temporanei in `{Reports}/_social-tmp` (video a pezzi, letti da `Mp4Info` prima di spedirli), cancellati subito e, se abbandonati, dal worker dopo un giorno.
- Su Bunny i file sono **sempre cifrati** (`MediaCipher`): busta con DEK casuale per file cifrata dalla KEK versionata (`KeyRing`), contenuto a blocchi da 1 MiB AES-256-GCM, nonce = indice del blocco, e nei dati associati tenant, media, variante (originale/miniatura), lunghezza, indice e "ultimo blocco": un file spostato, troncato o con blocchi scambiati non si decifra. L'intestazione (93 byte) dice dove sta ogni blocco, così un `Range` scarica da Bunny solo i blocchi che servono (Range su Bunny non è documentato: se risponde 200 si salta fino all'offset). Bunny non vede mai il chiaro, non serve una pull zone e il suo indirizzo non esce: la rotta firmata scarica, decifra e risponde con `MediaStreamResult` (206/416). Le copie passano dal server (decifra e ricifra con la chiave del media nuovo), senza chiaro su disco. La password della zone non va mai in risposte, log o messaggi d'errore.
- Miniature (~400 px JPEG) e pulizia: il browser le fa (`image.ts`: dal JPEG, o da un fotogramma per i video) e le manda a `POST /social/media/{id}/thumbnail` (anche per i file già nei post che non ce l'hanno, quelli dell'API pubblica, la prima volta che il pannello li mostra: `ensureThumbnail`). Il worker, nel giro orario, cancella gli originali dei post usciti su **tutti** gli account da `Media:CleanupAfterDays` giorni (7), `OriginalDeletedAtUtc`, **solo per i file che hanno la miniatura** (quelli di prima delle miniature o dell'API pubblica mai aperti nel pannello restano); un post con un account fallito li tiene. Dopo, la risposta ha `url: null`, `thumbnailUrl` e `originalDeleted`. I post ricorrenti tengono il loro modo: ogni uscita copia i file della serie (una modifica della serie non tocca un'uscita già creata o in ritentativo) e la copia si pulisce come ogni post.
- `SocialPublishWorker` ogni 15 s pubblica i target `Pending` di post non in bozza e già arrivati all'ora; errori passeggeri ritentati a 2/4/8 min (`MaxAttempts`), 401/token revocato → account `NeedsReconnect`. Al riavvio un target rimasto `Publishing` si riprova solo dove non crea doppioni (Mastodon con `Idempotency-Key` = id del target, Instagram e Threads con il container salvato in `ProgressState`), altrove diventa `Failed`.
- Reti: Bluesky con password per app (sessione aperta a ogni pubblicazione, link e hashtag come facet con estremi in **byte UTF-8**); Mastodon con token incollato (limite di caratteri letto dall'istanza); Meta (Graph API, versione in `Social:Meta:GraphVersion`) per Instagram e Pagine con un solo login, configurato per istanza con `Social:Meta:AppId/AppSecret` (`META_APP_ID`/`META_APP_SECRET` nel compose); Instagram Login (`InstagramLoginClient`, per gli account senza Pagina) con `Social:Instagram:AppId/AppSecret` (`INSTAGRAM_APP_ID`/`INSTAGRAM_APP_SECRET`, l'Instagram App ID, non quello Meta). Gli account Instagram sono una rete sola: `ServerUrl` = `https://graph.instagram.com` per Instagram Login, null se collegati tramite Pagina; `MetaGraphClient.InstagramBase` sceglie l'host. Il token di Instagram Login scade (`TokenExpiresAtUtc`, 60 giorni): il worker lo rinnova una volta l'ora quando ne restano meno di 53, e uno scaduto rende l'account `NeedsReconnect`.
- Threads (`ThreadsClient`, `graph.threads.net`, `Social:Threads:AppId/AppSecret` = `THREADS_APP_ID/SECRET`, il Threads App ID del caso d'uso, non l'app Meta): login con Threads (callback `/social/threads/callback`), token di 60 giorni rinnovato dal worker come quello di Instagram Login (`th_refresh_token`). Pubblica come Instagram: container `TEXT`/`IMAGE`/`VIDEO`/`CAROUSEL` (file scaricati da Threads dall'indirizzo firmato), stato, `threads_publish`. Importazione da `/me/threads` senza i `REPOST_FACADE`.
- Login Meta e Instagram: tornano a pagine del pannello (`/social/meta/callback`, `/social/instagram/callback`, su `Social:AppUrl` = `Auth:PublicAppUrl`), che passa codice e `state` all'API con la sessione: nessuna rotta anonima scrive nel tenant. `state` e scelta degli account sono protetti con DataProtection a scadenza; la scelta contiene i token di Pagina cifrati.
- Immagini: le converte in JPEG sotto 1 MB il browser (`src/social/image.ts`), il server verifica solo l'intestazione (`JpegInfo`). Instagram e Facebook le scaricano da `/api/v1/social/media/{tenant}{media}.jpg?e=&s=` (la miniatura `….thumb.jpg`, con una firma sua): rotta anonima, HMAC con chiave derivata (HKDF) dalla master, scadenza di un'ora; le stesse firme (12 h) servono le anteprime del pannello. L'indirizzo delle immagini è `Social:PublicUrl` (se manca, `Auth:PublicAppUrl`) e deve essere raggiungibile da internet; in sviluppo basta un quick tunnel verso l'API (`cloudflared tunnel --url http://localhost:5080` e `Social__PublicUrl=<indirizzo del tunnel>`), mentre i login tornano su localhost.
- Importazione (`SocialImporter`, chiamato dal worker dopo la pubblicazione): ogni 30 minuti per account (`LastImportAtUtc`) legge i post usciti fuori da ElephantSight, la prima volta degli ultimi 90 giorni, poi dall'ultima lettura con un giorno di sovrapposizione. Diventano `SocialPost` con `IsImported` (sola lettura: niente modifica né cancellazione, tornerebbero) e un target `Published`; i doppioni, compresi i post usciti da qui, si riconoscono da rete + `ExternalId`. Le anteprime si scaricano subito sul server (`RemoteImageClient`, solo https e JPEG, gli indirizzi dei CDN scadono). Bluesky si legge dall'AppView pubblica senza password; i post programmati in Business Suite non sono leggibili via API.
- Chiavi API e coda (`Api/Features/PublicApi`): `ApiKey` (globale, solo hash SHA-256, prefisso `wsk_`, mostrata una volta) apre le rotte `/api/v1/public` con `Authorization: Bearer wsk_…` (il gestore JWT le salta in `OnMessageReceived`; 120 richieste/minuto per chiave). Un programma esterno manda post con `type` (`text`, `image`, `carousel` da 2 a 10 immagini; facoltativo ma, se c'è, controllato contro le immagini), `externalRef` idempotente e `suggestedAtUtc` facoltativa: uno alla volta (`POST /public/media` per i JPEG, poi `POST /public/posts` in JSON con `media[].id`) o fino a 50 in una chiamata (`POST /public/posts/batch`, multipart: campo `posts` con l'array JSON, i file citati per nome in `media[].file`; ogni post si controlla e si salva da solo e la risposta dice `created`/`existing`/`rejected`, e un rifiutato non lascia file). I post diventano `SocialPost` con `IsInbox` (e bozza: il worker non li tocca), fuori dal calendario. La chiave non sceglie account né pubblica: dal pannello (`/social/inbox`, `POST /social/inbox/assign` per più post insieme) si assegnano account e ora e il post esce dalla coda (`LeaveInbox`, anche salvando dall'editor con "Programma"; "Salva in coda" lo lascia lì).
- Video (`SocialMedia.Kind`): MP4/MOV caricati come sono, senza ricodifica; `Mp4Info` legge da disco durata (mvhd), dimensioni (tkhd della traccia "vide", girate se la matrice è ruotata) e se l'indice è in testa (`FastStart`, obbligatorio per i Reel). Un video va da solo nel post. Instagram lo pubblica come Reel (`media_type=REELS`, `share_to_feed` = `PostOptions.InstagramShowInGrid`, "Mostra nella griglia del profilo"); le altre reti (salvo TikTok) non ricevono video. Caricamento a pezzi (`SocialMediaFiles.MapChunkedUploads`, pannello e `/public`): start → `PUT ?offset=` (fino a 50 MB, idempotente sull'offset) → complete, perché Cloudflare gratuito ferma le richieste oltre 100 MB; i `.part` (in `_social-tmp`) abbandonati li cancella il worker.
- Elaborazione lunga (Reel, TikTok): il publisher lancia `StillProcessingException` e il target torna `Pending` fra 30 s senza consumare tentativi (`StillProcessing`), con il container/publish_id in `ProgressState`; oltre 2 ore (`ProgressStartedAtUtc`) si arrende.
- TikTok (`TikTokClient`, `Social:TikTok:ClientKey/ClientSecret`, `TIKTOK_CLIENT_KEY/SECRET`): login OAuth (callback `/social/tiktok/callback`), token di 24 ore + rinnovo di un anno cifrati insieme (`TikTokSecret`), rinnovati dal worker sotto le 2 ore e dal publisher prima di pubblicare. Pubblicazione Direct Post con FILE_UPLOAD (un pezzo fino a 64 MB, poi pezzi da 10 MB, l'ultimo prende il resto), `creator_info` prima di ogni post e poi `status/fetch`. Le regole UX di TikTok sono nel pannello (`NetworkOptions.tsx`): account mostrato, visibilità senza predefinito (dalle `privacy_level_options` del creator), commenti/duetti/stitch spenti di default e disattivati se il creator li ha spenti, contenuto commerciale con le due caselle, frase di consenso. Le scelte stanno in `SocialPost.OptionsJson` (`PostOptions`, per post) e `SocialRules.OptionProblems` le controlla; dall'API pubblica si sceglie solo la griglia di Instagram, la visibilità TikTok la sceglie una persona. App non approvata da TikTok: solo `SELF_ONLY` su account privati. Foto su TikTok non fatte (vogliono un dominio verificato).
- Account su più post insieme (`POST /social/posts/accounts`, `BulkAccounts.tsx` nel calendario in modalità selezione): aggiunge e/o toglie account ai post scelti o a tutti quelli ancora da uscire; ogni post si controlla con gli account che avrebbe dopo, e quelli già usciti, che resterebbero senza account o che non vanno bene per la rete restano com'erano con il motivo.
- Post ricorrenti (`SocialRecurringPost`, `SocialRecurringEndpoints`, `Web/src/social/RecurringEditor.tsx`): contenuto, `AccountIds` (uuid[], un account scollegato si toglie anche da qui) e regola (`RecurrenceRule`: giornaliera/settimanale/mensile ogni `Interval`, ora locale nel fuso IANA del browser, inizio e fine; il mensile prende il giorno da `StartDate`, l'ultimo del mese se manca). **Le uscite non si preparano in anticipo**: quando arriva `NextOccurrenceUtc` il worker (`RecurringPostScheduler`, prima della pubblicazione nello stesso giro) crea un `SocialPost` normale con `RecurringPostId` e una copia dei file (`SocialMedia.CopyFor` + `SocialMediaStorage.Copy`; i file della serie hanno `RecurringPostId` al posto di `PostId`), poi ricalcola la prossima. Così una modifica vale per tutte le uscite future; il calendario le mostra calcolandole (`/social/recurring/occurrences`). Un'uscita in ritardo di più di un'ora (`MissedAfter`, server spento) si salta; riprendere dalla pausa riparte dalla prossima dopo adesso. Cancellare la serie lascia i post già usciti (`RecurringPostId` → null).
- I limiti delle reti stanno in `SocialRules` (server, controllati quando si programma; le bozze no) e in `src/social/rules.ts` (contatori del pannello): vanno cambiati insieme.
- Test: `FlarelyticsAppFactory.SocialApis` è un `FakeStoreServer` attaccato ai client delle reti (`SocialClients`); per le uscite ricorrenti i test spostano `NextOccurrenceUtc` nel passato con un `UPDATE` e chiamano il worker.

## Deploy
`Dockerfile` e `compose.yaml` alla radice: un'immagine sola (pannello + API + sincronizzazione, porta 8080, dati in `/data`) e PostgreSQL. Volumi: `flarelytics-keys` (chiave master e chiave dei JWT: da salvare **a parte** dai dati; servono anche per leggere i file dei post su Bunny), `flarelytics-backups` (i backup cifrati con la password del pannello), `flarelytics-data` (credenziali cifrate), `flarelytics-reports` (report grezzi, icone e, se lo storage è locale, i file dei post), `postgres-data`. File dei post su Bunny: `MEDIA_STORAGE`, `BUNNY_STORAGE_ZONE`, `BUNNY_STORAGE_REGION`, `BUNNY_STORAGE_ACCESS_KEY`, `MEDIA_CLEANUP_AFTER_DAYS` nel compose (o dal pannello, salvo la modalità). `deploy/postgres/10-app-role.sh` crea il ruolo applicativo non superutente: senza, la RLS non varrebbe.
